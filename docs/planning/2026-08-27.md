# CampusHub – Session Plan 2026-08-27

## Goal

Die Persistence-Schicht von CampusHub auf einen stabilen V1-Stand bringen und
anschließend die Grundlage für die Datenerfassung über Collector schaffen.

Am Ende der Session soll möglichst erstmals die vollständige Datenkette
durchlaufen werden können:

Source
  -> Collector
  -> CampusHub
  -> Repository
  -> PostgreSQL
  -> API
  -> JSON Response

Dabei wird zunächst mit Mock-Daten gearbeitet. Eine Anbindung realer
Infrastruktur ist ein optionales Stretch Goal.

---

## 1. BaseRepository fertigstellen

### Ziel

Das BaseRepository stellt die allgemeinen CRUD-Operationen bereit, ohne
Kenntnis konkreter Entities.

### Aufgaben

- `get_all()`
- `get_by_id()`
- `create()`
- `update()`
- `delete_by_id()`
- bestehende Methoden testen
- Rückgabeverhalten vereinheitlichen
- Context Manager für DB-Zugriffe verwenden
- SQL-Identifier und Query-Parameter weiterhin sauber trennen

### Ergebnis

CRUD-Grundfunktionen sind unabhängig von konkreten Tabellen wiederverwendbar.

---

## 2. Entity-Models und Repositories

### Ziel

Die allgemeinen Funktionen des BaseRepository für die CampusHub-Entities
nutzbar machen.

### Models

Bestehende Models prüfen bzw. ergänzen:

- Device
- Interface
- Metric
- Event
- User
- DeviceAssignment

Für Create-Operationen passende Input-Models ergänzen, z. B.:

- DeviceCreate
- InterfaceCreate
- MetricCreate
- EventCreate
- UserCreate

Create-Models enthalten nur Daten, die vom Client bzw. CampusHub geliefert
werden. Von PostgreSQL erzeugte Werte wie IDs gehören nicht hinein.

### Repositories

Konkrete Repositories erstellen:

- DeviceRepository
- InterfaceRepository
- MetricRepository
- EventRepository
- UserRepository
- DeviceAssignmentRepository

Zunächst nur notwendige Wrapper und tatsächlich benötigte Spezialqueries
implementieren.

Keine Methoden auf Vorrat bauen.

---

## 3. Datenbank-Migrationen / reproduzierbares Schema

### Ziel

Eine neue CampusHub-Instanz darf nicht davon abhängen, dass Tabellen manuell
in psql erstellt werden.

### Recherche

Geeignete Strategie für Schema-Migrationen untersuchen.

Mögliche Richtungen:

- einfache versionierte SQL-Migrationen
- bestehendes Python-Migrationstool

### Anforderungen

Eine Lösung sollte mindestens ermöglichen:

- leere Datenbank auf aktuellen Schema-Stand bringen
- Änderungen versionieren
- Migrationen reproduzierbar ausführen
- Schema-Änderungen gemeinsam mit dem Code committen

### Minimum für V1

Es muss möglich sein, aus einer leeren `campushub`-Datenbank das aktuelle
Schema automatisiert wiederherzustellen.

---

## 4. Collector-Architektur entwerfen

### Ziel

Festlegen, wie CampusHub Daten aus unterschiedlichen Infrastruktur-Komponenten
einsammelt, ohne den restlichen Code an SNMP, SSH oder eine bestimmte API zu
koppeln.

### Zuerst klären

- Was ist die Verantwortung eines Collectors?
- Welche Daten liefert ein Collector?
- Wie werden Fehler dargestellt?
- Kennt ein Collector die Datenbank?
- Kennt ein Collector Repositories?
- Wer entscheidet, wann gesammelt wird?
- Wie unterscheiden wir verschiedene Protokolle?
- Wie identifizieren wir Geräte eindeutig?

### Geplanter Datenfluss

Infrastructure / Mock Source
        |
        v
     Collector
        |
        v
    collected data
        |
        v
  CampusHub Services
        |
        v
   Repositories
        |
        v
    PostgreSQL

Collector sollten möglichst keine SQL- oder Datenbanklogik enthalten.

---

## 5. Collector-Interface / gemeinsame Struktur

### Ziel

Eine gemeinsame Schnittstelle definieren, an die sich spätere Collector halten
können.

Mögliche Collector:

- MockCollector
- SNMPCollector
- LinuxCollector
- RESTCollector
- weitere Adapter bei Bedarf

Noch keine vollständige Implementierung aller Varianten.

Zuerst muss geklärt werden, welche gemeinsamen Informationen sinnvoll
abgebildet werden können.

Beispiele:

- Device Information
- Interfaces
- Metrics
- Events

Die Collector-Struktur soll reale Unterschiede zwischen Datenquellen zulassen
und nicht versuchen, jedes Gerät künstlich identisch zu behandeln.

---

## 6. MockCollector implementieren

### Ziel

Die komplette CampusHub-Pipeline ohne Abhängigkeit von realer
Schulinfrastruktur testen können.

Der MockCollector soll realistische Testdaten erzeugen, beispielsweise:

- Device-Metadaten
- Interfaces
- CPU-Auslastung
- RAM-Auslastung
- Storage
- Temperatur
- Uptime
- Events

Die Daten müssen nicht perfekt simuliert werden.

Wichtig ist zunächst nur:

MockCollector
  -> CampusHub
  -> PostgreSQL

---

## 7. Erster vollständiger End-to-End-Test

Dieser Schritt erfolgt erst, sobald Collector und Persistence-Schicht
ausreichend funktionieren.

### Ziel

Ein Datensatz soll erstmals den kompletten CampusHub-Weg durchlaufen.

Beispiel:

MockCollector
  -> Device / Metric erzeugen
  -> Service
  -> Repository
  -> PostgreSQL
  -> FastAPI
  -> GET Endpoint
  -> JSON

Hierfür reicht zunächst ein einzelner Endpoint, beispielsweise:

`GET /devices`

Es ist nicht das Ziel, bereits die komplette REST-API umzusetzen.

### Meilenstein

Wenn dieser Ablauf funktioniert, sind die wichtigsten technischen Schichten
erstmals miteinander verbunden.

---

## 8. Stretch Goal: echte Infrastruktur

Nur bearbeiten, wenn die vorherigen Schritte sauber genug funktionieren.

Mögliche erste Tests:

- ein Cisco-Gerät über SNMP abfragen
- Hostname auslesen
- Uptime auslesen
- Interface-Informationen auslesen

oder eine andere verfügbare Infrastrukturquelle verwenden.

Ziel ist ausdrücklich noch keine vollständige SNMP-Implementierung.

Ein einziger realer Wert, der erfolgreich durch CampusHub bis PostgreSQL
gelangt, wäre bereits ein Erfolg.

## Session-Abschluss

Stattdessen:

- offene TODOs dokumentieren

- relevante Dokumentation aktualisieren

## Prioritäten

### Must Have

1. BaseRepository CRUD fertig
2. Create-Models
3. konkrete Repositories
4. Migration-Strategie festlegen / beginnen
5. Collector-Architektur verstehen und entwerfen

### Should Have

6. MockCollector
7. Mock-Daten persistieren

### Nice To Have

8. erster End-to-End-Slice
9. erste reale Infrastrukturabfrage

---

## Nicht für diese Session

Bewusst nicht priorisieren:

- vollständiges Frontend
- Dashboard-Design
- vollständige REST-API
- Authentication / Authorization
- sämtliche Spezialqueries
- vollständige SNMP-Unterstützung
- Performance-Optimierung
- Deployment-Optimierung

Das Ziel dieser Session ist das Fundament, nicht Feature-Vollständigkeit.
