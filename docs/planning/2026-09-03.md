# CampusHub – Next Session Plan

## Goal

Die bestehende Persistence-Schicht mit der ersten fachlichen Service-Logik und
einer Collector-Struktur verbinden.

Am Ende der Session soll CampusHub erstmals Monitoring-Daten aus einer
definierten Quelle entgegennehmen, fachlich verarbeiten und in PostgreSQL
speichern können.

Die Quelle kann zunächst ein MockCollector sein.

Langfristiges Ziel:

Infrastructure
    -> Collector / Log Source
    -> Service
    -> Repository
    -> PostgreSQL
    -> API
    -> Dashboard / Live Event Feed

---

# 1. Repository-Layer kurz abschließen

## Ziel

Den aktuellen Repository-Stand nur noch konsolidieren, nicht weiter ausbauen.

### Aufgaben

- bestehende Repositorys einmal prüfen
- Imports und Naming kontrollieren
- temporäre Testdateien aufräumen
- BaseRepository dokumentieren
- offene Type-Hint-Warnungen notieren

Keine weitere Repository-Abstraktion in dieser Session.

---

# 2. Ersten echten Service erstellen

## Ziel

Eine fachliche Schicht zwischen API / Collector und Repository einführen.

Start mit:

DeviceService

Mögliche Verantwortung:

- Devices laden
- Device anlegen
- Device aktualisieren
- Device löschen
- später fachliche Validierung
- später Zugriffsrechte prüfen
- später Collector-Daten einem Device zuordnen

Der Service soll keine SQL-Logik enthalten.

Datenfluss:

Caller
    -> DeviceService
    -> DeviceRepository
    -> BaseRepository
    -> PostgreSQL

Zunächst reicht eine kleine, transparente Implementierung.

---

# 3. Monitoring-Domain definieren

## Ziel

Festlegen, welche Arten von Informationen CampusHub überhaupt sammeln soll.

### Device Data

Beispiele:

- hostname
- device_type
- location
- interfaces

### Metrics

Beispiele:

- CPU usage
- RAM usage
- storage usage
- temperature
- uptime

### Events

Beispiele:

- device online
- device offline
- interface down
- interface up
- SNMP timeout
- authentication failure
- CPU threshold exceeded
- storage threshold exceeded

Diese drei Datenarten bilden zunächst den Kern der Monitoring-Funktion.

---

# 4. Collector-Architektur entwerfen

## Ziel

Collector sollen Daten aus unterschiedlichen Quellen sammeln können, ohne dass
der restliche CampusHub-Code an ein bestimmtes Protokoll gekoppelt wird.

Mögliche zukünftige Collector:

- MockCollector
- SNMPCollector
- LinuxCollector
- RESTCollector
- SyslogReceiver

Ein Collector soll keine SQL-Queries ausführen.

Geplanter Ablauf:

Device / Source
    -> Collector
    -> strukturierte Daten
    -> Service
    -> Repository
    -> PostgreSQL

Zu klären:

- Welche Methoden besitzt ein Collector?
- Welche Datenobjekte gibt ein Collector zurück?
- Wie werden Fehler dargestellt?
- Wie wird ein Gerät identifiziert?
- Wer startet einen Collector?
- Wie oft wird gesammelt?
- Wie werden Collector-Fehler zu Events?

---

# 5. MockCollector bauen

## Ziel

Monitoring-Daten erzeugen können, ohne von realer Infrastruktur abhängig zu
sein.

Der MockCollector soll realistische Beispieldaten erzeugen.

Beispiele:

Device:
- hostname
- device_type
- location

Metric:
- CPU
- RAM
- storage
- temperature
- uptime

Event:
- interface down
- device online
- high CPU usage

Die Werte dürfen statisch oder leicht zufällig sein.

Ziel ist nicht Simulationstreue, sondern eine funktionierende Datenpipeline.

---

# 6. Ersten Monitoring-Service bauen

## Ziel

Collector-Ausgaben nicht direkt in Repositorys schreiben lassen.

Möglicher Ablauf:

MockCollector
    -> MonitoringService
    -> MetricRepository
    -> EventRepository
    -> PostgreSQL

Mögliche Verantwortlichkeiten:

- Collector-Ergebnisse entgegennehmen
- Daten validieren
- Metrics speichern
- Events erzeugen
- später Grenzwerte prüfen
- später Statusänderungen erkennen

Beispiel:

CPU = 92 %

MonitoringService
    -> Metric speichern
    -> Threshold prüfen
    -> Event erzeugen:
       "CPU usage above threshold"

Damit beginnt CampusHub erstmals eigene fachliche Monitoring-Logik zu besitzen.

---

# 7. Event-System vorbereiten

## Ziel

Events als zentrale Informationsquelle für das spätere Dashboard etablieren.

Events sollen mindestens enthalten:

- device_id
- timestamp
- type
- description

Später mögliche Erweiterungen:

- severity
- source
- resolved
- category

Beispiele:

INFO
- Device successfully polled

WARNING
- CPU usage above threshold

ERROR
- SNMP request failed

CRITICAL
- Device unreachable

Noch keine komplette Severity-Implementierung notwendig.
Architektur lediglich vorbereiten.

---

# 8. Live Event Feed als zukünftiges Dashboard-Feature festhalten

## Zielbild

Das spätere Dashboard soll aktuelle Events nahezu in Echtzeit darstellen.

Beispiel:

14:32:05  switch-campus-1  Interface Gi0/2 DOWN
14:31:48  server-dns-01    CPU usage above 80%
14:31:12  firewall-01      SNMP timeout
14:30:55  switch-campus-2  Device online

Erste Version:

Dashboard
    -> GET /events
    -> sortiert nach timestamp DESC
    -> regelmäßiges Polling

Spätere Erweiterung:

- Server-Sent Events
oder
- WebSockets

Damit können neue Events automatisch im Dashboard erscheinen.

# Future Monitoring Sources

Später mögliche Erweiterungen:

## SNMP

Pull-basierte Abfrage von:

- Device Status
- Uptime
- Interfaces
- Counters
- weitere MIB-Werte

## Syslog

Push-basierte Events von:

- Linux-Systemen
- Routern
- Switches
- Firewalls

Sehr interessant für den späteren Live Event Feed.

## Health Checks

Beispiele:

- ICMP / Ping
- HTTP Status
- TCP Port Reachability

## Network Analysis

Packet Capture / Flow Analysis ist als mögliche Erweiterung denkbar,
gehört jedoch zunächst nicht zum Kernscope.

Insbesondere mit späteren Red-Team-/Blue-Team-Übungen könnte eine
Erweiterung in Richtung Netzwerk-Analyse interessant werden.

Für V1 bleibt der Schwerpunkt jedoch:

- Monitoring
- Logging
- Metrics
- Events
- zentrale Übersicht
